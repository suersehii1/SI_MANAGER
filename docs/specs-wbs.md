## W1. 개요

- WBS는 프로젝트 하위의 **계층형 작업 트리**(최대 깊이 5). 각 노드는 작업명, 산출물, 담당자, 상태, 가중치, 계획/실제 기간, 진척률을 가진다.
- **리프(leaf) 노드만** 기간·진척률·상태를 직접 입력한다. **부모 노드**의 기간·진척률·상태는 하위 노드로부터 **집계(roll-up)** 되며 읽기 전용이다.
- WBS 코드(`1`, `1.2`, `1.2.3`)는 저장하지 않고 트리 순서(`sort_order`)로 **조회 시 계산**한다 → 순서 변경 시 코드 자동 재번호.
- 조회: 모든 인증 사용자. 작성/수정/삭제/이동: **ADMIN 또는 해당 프로젝트에 할당(project_assignments)된 사용자**.

## W2. DDL — `backend/src/main/resources/db/migration/V3__wbs.sql`

```sql
-- ===== wbs_items =====
CREATE TABLE wbs_items (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id    BIGINT        NOT NULL,
    parent_id     BIGINT,
    sort_order    INTEGER       NOT NULL DEFAULT 0,
    name          VARCHAR(200)  NOT NULL,
    description   VARCHAR(4000),
    deliverable   VARCHAR(200),
    assignee_id   BIGINT,
    status        VARCHAR(20)   NOT NULL DEFAULT 'NOT_STARTED',
    weight        NUMERIC(5,2)  NOT NULL DEFAULT 1.00,
    planned_start DATE,
    planned_end   DATE,
    actual_start  DATE,
    actual_end    DATE,
    progress      INTEGER       NOT NULL DEFAULT 0,
    created_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_wbs_name CHECK (LENGTH(TRIM(name)) > 0),
    CONSTRAINT ck_wbs_status CHECK (status IN ('NOT_STARTED', 'IN_PROGRESS', 'DONE', 'ON_HOLD')),
    CONSTRAINT ck_wbs_weight CHECK (weight > 0 AND weight <= 999.99),
    CONSTRAINT ck_wbs_progress CHECK (progress BETWEEN 0 AND 100),
    CONSTRAINT ck_wbs_sort_order CHECK (sort_order >= 0),
    CONSTRAINT ck_wbs_planned_period CHECK (
        planned_start IS NULL OR planned_end IS NULL OR planned_end >= planned_start),
    CONSTRAINT ck_wbs_actual_period CHECK (
        actual_end IS NULL OR (actual_start IS NOT NULL AND actual_end >= actual_start)),
    CONSTRAINT fk_wbs_project  FOREIGN KEY (project_id)  REFERENCES projects (id)  ON DELETE CASCADE,
    CONSTRAINT fk_wbs_parent   FOREIGN KEY (parent_id)   REFERENCES wbs_items (id) ON DELETE CASCADE,
    CONSTRAINT fk_wbs_assignee FOREIGN KEY (assignee_id) REFERENCES users (id)     ON DELETE SET NULL
);
CREATE INDEX ix_wbs_project_parent_order ON wbs_items (project_id, parent_id, sort_order);
CREATE INDEX ix_wbs_parent ON wbs_items (parent_id);
CREATE INDEX ix_wbs_assignee ON wbs_items (assignee_id);
```

| FK | 동작 | 이유 |
|---|---|---|
| wbs_items → projects | CASCADE | 프로젝트 삭제 시 WBS 제거 |
| wbs_items.parent_id → wbs_items | CASCADE | 노드 삭제 시 하위 트리 전체 제거 |
| wbs_items.assignee_id → users | SET NULL | |

- 형제 간 `sort_order`는 서비스가 0..n-1로 연속 유지(삽입/이동/삭제 후 재정렬). DB UNIQUE는 두지 않음(NULL parent 처리 및 재정렬 중간 상태 때문).
- 부모와 자식은 반드시 같은 `project_id` (서비스 검증).
- ERD 추가: `projects ||--o{ wbs_items`, `wbs_items ||--o{ wbs_items : parent`, `users ||--o{ wbs_items : assignee`.

**JPA**: `WbsItem` 엔티티, `parent`는 `@ManyToOne(LAZY)`이되 **트리는 프로젝트 단위로 한 번에 조회**(`findByProjectIdOrderByParentIdAscSortOrderAsc` 등) 후 메모리에서 조립 — N+1 금지. `status`는 `@Enumerated(STRING)` `WbsStatus`, `weight`는 `BigDecimal(5,2)`.

## W3. 집계(Roll-up) 규칙 — `WbsRollupCalculator` (순수 클래스, 단위 테스트 대상)

트리를 후위 순회하며 계산. 리프는 저장값 그대로.

| 필드 | 부모 노드 계산 |
|---|---|
| `plannedStart` | 자식 `plannedStart` 중 non-null 최솟값 (없으면 null) |
| `plannedEnd` | 자식 `plannedEnd` 중 non-null 최댓값 |
| `actualStart` | 자식 `actualStart` 중 non-null 최솟값 |
| `actualEnd` | **모든** 자식의 `actualEnd`가 non-null이면 그 최댓값, 아니면 null |
| `progress` | `Σ(wᵢ × pᵢ) / Σ wᵢ` (wᵢ = 자식 weight, pᵢ = 자식의 집계된 progress). BigDecimal 계산 후 **소수 1자리 HALF_UP** |
| `status` | 모든 자식 DONE → DONE / 모든 자식 NOT_STARTED → NOT_STARTED / 모든 자식 ON_HOLD → ON_HOLD / 그 외 IN_PROGRESS |

- 리프의 `progress`는 정수(0..100)지만 응답 필드 `progress`는 모든 노드에서 숫자(소수 1자리)로 직렬화.
- **프로젝트 전체 진척률** `overallProgress` = 루트 노드들에 같은 가중 평균 적용(소수 1자리). 노드가 없으면 0.
- **지연(delayed)**: `plannedEnd != null && plannedEnd < asOf && progress < 100`. `asOf` = 오늘(Asia/Seoul), 쿼리 파라미터로 재정의 가능.
- `plannedDays` = `plannedStart..plannedEnd` 양끝 포함 일수(둘 중 하나라도 null이면 null).
- `wbsCode`: 루트는 `sort_order+1`, 자식은 `부모코드 + "." + (sort_order+1)`. `level`: 루트 1.

**리프 입력 규칙 (서비스)**
1. 상태/진척률 규칙 (위에서부터 처음 맞는 규칙 하나만 적용, 2026-10-23 QA O-04 결정으로 개정):
   1. **이미 DONE인 리프**에 `status = DONE`이면서 `progress < 100`인 요청이 오면(그리드에서 진척률만 낮춘 경우) → status를 **IN_PROGRESS로 전환**하고 progress는 요청값을 유지한다.
   2. `status`를 DONE으로 **바꾸는** 요청(신규 생성 포함, 이전 상태 ≠ DONE) → `progress`를 100으로 강제한다.
   3. `progress = 100`이고 status가 NOT_STARTED면 DONE으로 설정한다. `0 < progress < 100`이고 status가 NOT_STARTED면 IN_PROGRESS로 설정한다. (ON_HOLD는 유지)
2. 자식이 있는 노드에 대한 수정 요청의 `status/progress/plannedStart/plannedEnd/actualStart/actualEnd`는 **무시**(저장값 유지; 응답은 집계값). `name/description/deliverable/assigneeId/weight`만 반영.
3. 리프였던 노드에 자식이 처음 추가되면 그 노드의 저장된 기간/진척 값은 그대로 두되 이후 집계값만 노출.

### W3.1 Worked Example (QA 기준값 — V4 시드와 동일, asOf = 2026-03-15)

프로젝트 `SI-2026-001` (계획 2026-01-01 ~ 2026-03-31). 모든 weight = 1.00.

| WBS | 작업명 | 계획 | 실제 | 상태 | progress |
|---|---|---|---|---|---|
| 1 | 분석 | (집계) 01-01~01-31 | 01-15~01-31 | DONE | **100.0** |
| 1.1 | 요구사항 정의 | 01-01~01-15 | 01-15~01-20 | DONE | 100 |
| 1.2 | 현행 시스템 분석 | 01-16~01-31 | 01-21~01-31 | DONE | 100 |
| 2 | 설계 | (집계) 02-01~02-28 | 02-01~(null) | IN_PROGRESS | **90.0** |
| 2.1 | 화면 설계 | 02-01~02-14 | 02-01~02-16 | DONE | 100 |
| 2.2 | DB 설계 | 02-01~02-28 | 02-01~null | IN_PROGRESS | 80 |
| 3 | 개발 | (집계) 03-01~03-25 | 03-02~null | IN_PROGRESS | **25.0** |
| 3.1 | 공통 모듈 개발 | 03-01~03-15 | 03-02~null | IN_PROGRESS | 50 |
| 3.2 | 업무 화면 개발 | 03-10~03-25 | null | NOT_STARTED | 0 |
| 4 | 테스트 및 이행 | 03-26~03-31 | null | NOT_STARTED | 0 |

- `overallProgress` = (100 + 90 + 25 + 0) / 4 = **53.8** (53.75 → HALF_UP 1자리).
- 지연(asOf 2026-03-15): 2.2 (plannedEnd 02-28, 80%) → **true**, 2 (집계 plannedEnd 02-28, 90%) → **true**. 3.1 (plannedEnd 03-15, 같은 날은 지연 아님) → false.
- 2.2의 weight를 3.00으로 바꾸면 2 = (100×1 + 80×3)/4 = **85.0**, overall = (100+85+25+0)/4 = **52.5** (가중치 검증용).
- 시드 담당자: 1.x/2.x = 시드 데이터에서 SI-2026-001에 할당된 첫 번째 사용자, 3.x/4 = 두 번째 사용자(V2 시드의 username으로 `INSERT ... SELECT`). 해당 사용자가 없으면 NULL.

시드 파일: `V4__wbs_seed.sql` (이식성 규칙 동일, 부모 id는 `(SELECT id FROM wbs_items WHERE project_id = ... AND name = '분석' AND parent_id IS NULL)` 형태로 조회).

### 검증 & 에러 (specs.md §4.1 에러 코드 표에 추가)

| HTTP | code | 상황 |
|---|---|---|
| 400 | `VALIDATION_ERROR` + fieldError `DATE_RANGE` | `@DateRange(plannedStart, plannedEnd, false)`, `@DateRange(actualStart, actualEnd, true)` |
| 400 | `WBS_OUT_OF_PROJECT_PERIOD` | 리프의 계획 기간이 프로젝트 계획 기간을 벗어남 (fieldErrors `plannedStart`/`plannedEnd`) |
| 400 | `WBS_ASSIGNEE_NOT_MEMBER` | 담당자가 해당 프로젝트에 할당되지 않은 사용자 (fieldError `assigneeId`) |
| 400 | `USER_DISABLED` | 비활성 사용자를 담당자로 지정 |
| 400 | `WBS_INVALID_PARENT` | parentId가 다른 프로젝트 소속이거나 존재하지 않음 |
| 400 | `WBS_INVALID_MOVE` | 자기 자신 또는 자신의 하위 노드를 부모로 지정 |
| 400 | `WBS_DEPTH_EXCEEDED` | 생성/이동 결과 깊이가 5 초과(이동 시 서브트리 깊이 포함) |
| 403 | `FORBIDDEN` | ADMIN도 프로젝트 멤버도 아닌 사용자의 쓰기 요청 |

- 프로젝트 계획 기간 수정(#10) 시, 기존 WBS 리프 계획 기간이 범위를 벗어나면 기존 할당과 동일하게 409 `PROJECT_PERIOD_CONFLICT` (§5.2-5 확장).

```
       클라이언트 검증: 이름 필수, 종료일 ≥ 시작일(위반 시 API 호출 안 함), 프로젝트 계획 기간 밖이면 경고 표시
       저장 [wbs-form-submit] → create/update → emit saved → 트리 재조회
```

**AG Grid Community 제약**: `treeData`, row grouping, master/detail은 Enterprise 기능이므로 **사용하지 않는다.** 트리는 평탄화된 `items`(DFS 순서) + `level` 들여쓰기 + 접기 상태(`collapsedIds: Set`)로 직접 구현한다.

이동 헬퍼 규칙 (형제 = 같은 parentId, sortOrder 순):
- `moveUp`: index-1 (첫 번째면 무시) / `moveDown`: index+1 (마지막이면 무시)
- `indent`: 바로 위 형제를 새 부모로, index = 그 형제의 childCount (첫 번째 형제면 버튼 disabled)
- `outdent`: 새 부모 = 현재 부모의 parentId, index = 현재 부모의 sortOrder + 1 (루트면 disabled)
